## Deploy

```bash
# Interactive (no args — shows a menu)
sudo /opt/cykruit-v2/deploy.sh
#   1) cykruit-app  (all 10 microservices)
#   2) admin-app
#   3) cykruit-ui
#   4) admin-ui
#   5) migrate      (prisma migrate deploy)
#   6) All services (migrate + all 4 apps)
#   7) Build env    (pull secrets from SSM — replaces old build-env.sh)
#   8) Build env + Full deploy

# CI-mode (positional args, no prompts)
sudo /opt/cykruit-v2/deploy.sh <env> <target> <tag>
# targets: migrate | cykruit-app | admin-app | cykruit-ui | admin-ui
# tag: short git sha, or "latest"
```

`deploy.sh` auto-runs `docker system prune -af` and ECR login every time — no
separate cleanup step needed.

**Known bug in the interactive path**: options 1-6 call `prompt_tag()`, which
fetches the last 5 *pushed* images (not specifically per-service) and filters
for an `auth-service-` prefix — if none of the last 5 pushes happened to be
`auth-service`, the result is empty and the script silently exits under
`set -e` before ever showing the tag prompt. If this happens, either retry
(a later, different pushed image might match) or bypass the script entirely
with a manual `docker compose pull <service> && docker compose up -d <service>`
using tag `latest`. Not yet fixed as of this writing.

## Restart a single container without a full deploy

```bash
cd /opt/cykruit-v2 && sudo docker compose up -d --force-recreate <service-name>
```

No manual `export ENV=...`/`REDIS_PASSWORD=...` needed — `ENV`/`REDIS_PASSWORD`
are Compose-interpolation vars (used directly in `docker-compose.yml`, e.g.
redis's `${REDIS_PASSWORD}`), resolved from `/opt/cykruit-v2/.env` (Compose's
own project `.env`, distinct from `env_file:` and from `.env.prod`). `deploy.sh`'s
build-env step (option 7/8) keeps that file in sync automatically — just make
sure it's been run at least once since the last secret rotation.

## Nginx rate limiting (`/etc/nginx/sites-enabled/cykruit-v2`)

Add these zones at the **top of the http block** (or in `/etc/nginx/conf.d/rate-limit.conf`):

```nginx
# In /etc/nginx/conf.d/rate-limit.conf (create if missing)
limit_req_zone $binary_remote_addr zone=global:10m    rate=100r/s;
limit_req_zone $binary_remote_addr zone=auth_strict:10m rate=5r/m;
```

In each `server {}` block (all 4 domains), add inside the block:

```nginx
    # Global burst — allows short spikes, queues the rest
    limit_req zone=global burst=200 nodelay;
    limit_req_status 429;

    # Tight limit on auth mutation endpoints
    location ~* ^/(auth|api/auth)/(login|register|forgot-password|request-otp) {
        limit_req zone=auth_strict burst=3 nodelay;
        proxy_pass http://127.0.0.1:PORT;  # replace PORT per vhost
    }
```

Also ensure Nginx forwards real client IP to upstream containers:

```nginx
    # In every proxy_pass location
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Real-IP       $remote_addr;
```

After editing: `sudo nginx -t && sudo systemctl reload nginx`

## SSM Parameter Store / Secrets Manager (region `ap-south-1`)

- Params (recursive fetch): `/cykruit-v2/prod/backend/*` -> `.env.prod`,
  `/cykruit-v2/prod/admin-backend/*` -> `.env.prod.admin`
- Secrets: `/cykruit-v2/prod/backend/{db-password,jwt-secret,redis-password,resend-api-key,google-oauth,razorpay,aws-s3-credentials,ai-vendor-keys,bedrock-credentials(optional)}`,
  `/cykruit-v2/prod/admin-backend/{jwt-secret,resend-api-key}`
- Adding a new one? Just add the Parameter/Secret, then re-run `deploy.sh`'s
  build-env step (option 7/8) — no script change needed unless it's a
  computed/assembled value (like `DATABASE_URL`, assembled from
  `db-host`/`db-port`/`db-password`).
- `DATABASE_URL`, `REDIS_HOST`, `REDIS_PORT`, `REDIS_PASSWORD`, `EMAIL_FROM` are
  shared infra values copied into `.env.prod.admin` at build-env time (same RDS
  `cykruit` DB, same self-hosted `redis` container) — don't duplicate them as
  separate `admin-backend/` params.
- `aws-s3-credentials` should contain **only** the S3 bucket-name keys, not
  `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` — on EC2, S3 auth is meant to go
  through the instance role, not static keys (see Gotchas).

## Gotchas hit this session (don't repeat)

- `docker-compose.yml` `environment:` keys must be indented **2 spaces deeper**
  than `environment:` itself — a same-level key silently makes `environment`
  parse as `null`, not a mapping, and fails compose validation
  (`services.X.environment must be a mapping`) only when compose actually runs,
  not on save.
- `deploy.sh`'s `admin-app`/`admin-ui` targets used the ECR **image repo name**
  (`cykruit-admin-app`/`cykruit-admin-ui`) instead of the compose **service
  name** (`admin-app`/`admin-ui`) — fixed, but check for this class of mismatch
  if a new target is ever added.
- Next.js `output: "standalone"` resolves `next.config.ts`'s `rewrites()`
  destinations at `next build` time (baked into `.next/routes-manifest.json`).
  Container-runtime env vars (`docker-compose.yml` `environment:`) **cannot**
  override them — these must be passed as Docker build-args in CI instead.
  Same applies to `NEXT_PUBLIC_*` vars anywhere in the code (e.g.
  `NEXT_PUBLIC_WS_URL` in `cykruit-ui/proxy.ts`), since Next.js statically
  inlines them at build time regardless of client/server code.
- Every backend `main.ts` registered `/health` via `httpServer.get(...)`
  **after** `await app.listen(...)`. Nest finalizes its own routing (including
  a catch-all 404 handler) during `listen()`, so the raw Express route added
  afterward was never reachable — `/health` 404'd on every service since this
  pattern was first written, undetected until real healthchecks were added.
  Fix: register the route *before* `app.listen()`.
- Healthcheck `wget` commands must target `127.0.0.1`, not `localhost` — inside
  these containers `localhost` resolves to `::1` (IPv6) first, and nothing
  listens there (Node's `0.0.0.0` bind is IPv4-only), so `wget` gets
  `Connection refused` even though the app is up and `127.0.0.1` works fine.
- `libs/upload/src/upload.service.ts` used to pass an explicit `credentials`
  object to `S3Client` unconditionally, even when `AWS_ACCESS_KEY_ID`/
  `AWS_SECRET_ACCESS_KEY` were both unset. The AWS SDK v3 treats any explicitly
  provided `credentials` as authoritative and skips its own default provider
  chain — so on EC2 (where these are intentionally left unset for the instance
  role to authenticate) every S3 call would silently use an empty/invalid
  credentials object instead. Fixed to only include `credentials` when both
  values are actually present, matching the existing correct pattern in
  `libs/ai/src/providers/bedrock.provider.ts`.
